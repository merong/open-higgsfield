# AI·사람 공통 실행 지침

suite `agentic-pages-v1` / 2026-09-29. [목록](README.md)에서 케이스를 고르고 [양식](run-template.md)을 복사한다. 시나리오 문서의 기대 결과는 **검사자 전용**이다. 제작 AI에게는 그 시점의 사용자 입력과 첨부 자료만 보낸다.

## 실행 계약

1. `baseline`은 현행 동작을 그대로 측정한다. 기존 필수 승인 화면을 통과하더라도 승인 횟수를 기록하고 목표 UX와의 차이를 남긴다. `candidate`는 개선된 버전에서 같은 입력·자료·사용자 분기로 다시 실행한다. 미구현 기능을 테스트 중 수정하거나 몰래 우회해 baseline을 바꾸지 않는다.
2. 실제 UI에서 랜딩 또는 제품 상세의 **AI와 함께 제작**으로 시작한다. 현재 지원하지 않는 입력 유형/수정 기능은 `unsupported`. 수동 입력 등 대안은 별도 run이며 원래 항목의 성공으로 대체하지 않는다. 결과를 DB에 직접 삽입하여 UI 성공을 만들지 않는다.
3. 각 run은 새 프로젝트를 사용하고 suite/case ID와 실제 project ID를 양식에 연결한다. 모델·effort·앱 revision·dirty 소스 해시·화면 크기·fixture 해시를 고정한다. 시나리오 제목은 추적용 메타데이터이며 제작 프롬프트에 추가하지 않는다.
4. 기본 viewport는 데스크톱 1440×1000, 모바일 390×844. 실제 결과를 양쪽에서 확인한다. 개발 관찰실은 로컬 PGlite / `DATABASE_URL` 미설정 환경이다. 이 조건이 없으면 제작 결과와 trace 검증의 판정을 분리한다.
5. 실행 전에 계정·사용 환경·텍스트/이미지 호출 허용 범위·크레딧 상한·최대 재시도/대기시간을 기록한다. 이미 사용자 지침에 있으면 다시 묻지 않는다. 이번 문서 작성 자체가 유료 E2E 실행이나 게시 지시는 아니다. 예산이 소진되면 `blocked_budget`로 끝내고 관측 내용을 보존한다. 모의 provider로 진행하면 `mock`이라고 표시하며 실모델 E2E로 집계하지 않는다.

## 사용자 역할과 단계 진행

- 최초에는 케이스의 **최초 입력**만 복사한다. URL/사진/한 문장 중 정해진 하나로 시작하고 숨겨진 답변이나 추후 피드백을 먼저 보내지 않는다.
- 사진·URL에서 확인한 사실과 제작 AI의 추정을 구분한다. 검사자가 알고 있는 정답을 테스트 중 몰래 보충하지 않는다.
- 예상 질문이 오면 케이스에 정한 답만 제공한다. 불필요한 스타일/배치 질문은 `스타일과 배치는 알아서 정해 주세요. 제공하지 않은 사실은 빼고 진행해 주세요.`로 한 번 답하고 부담으로 센다.
- 케이스에 답이 없는 상품 사실은 `그 정보는 아직 없으니 제외해 주세요.`로 답한다. 대상 자체가 결정되지 않으면 `blocked_input`으로 기록한다. 새로운 사실을 임의 창작해 성공시키지 않는다.
- 초안이 실제 표시되고 저장된 뒤에만 다음 피드백을 보낸다. 여러 턴을 합치지 않는다. 분기 조건이 없는데 실패를 가정하지 않는다.
- 원하지 않는 이미지가 나온 경우 해당 장면·슬롯을 지정해 정해진 피드백을 입력한다. 요청 해석/수정/적용/시각 결과를 각각 검사한다. 예상 장면이 이미 좋더라도 케이스의 선호 변경 요청은 실행 가능하나, 실제로 없던 결함이 발생했다고 보고하지 않는다.
- 선택 영역 기능이 없다면 영역 검사는 `unsupported`로 남긴다. 같은 텍스트를 일반 수정창에 넣는 대체 검사는 별도 항목으로 분리한다.
- 재생성 후에도 사용자의 요청을 충족하지 못한 경우에만 추가 분기: `아직 요청한 부분이 해결되지 않았어요. 내용·구도·크기·모델 중 무엇을 바꿔야 하는지 짧게 제안해 주세요.`를 보낸다. 제안한 변경과 실제 호출 설정을 대조하고, 추가 비용/상품 정체성 변경 등 판단이 필요한 경우만 확인하는지 본다. 실행 한도 안에서 선택한 변경을 수행하며 변경할 필요가 없는 설정은 유지한다. 이 분기를 쓴 run은 같은 분기끼리 비교한다.
- 저장/복원 후 새로고침·재접속하여 실제 영속 결과를 확인한다. 고객 사이트에 공개하거나 구매/신청을 실제 제출할 필요는 없다. CTA는 목적·레이블·설정된 URL/미설정 상태를 확인하고 허위 동작 성공을 주장하지 않는다.

## 공통 체크포인트

| ID | 확인 시점 | 증거와 목표 |
|---|---|---|
| C1 | 최초 요청→초안 | 추가 질문·필수 승인·입력 횟수. 대상이 명확하면 스타일/미제공 가격 때문에 막지 않음 |
| C2 | 기획/생성 직전 | 이미지 총수 N, 슬롯별 역할·내용·비율, 요청 픽셀/모델, 새 생성/원본 재사용/생략 구분 |
| C3 | 첫 결과 | 실제 출력 파일 규격과 화면 표시 크기·크롭 별도 기록. 미제공 후기·수치·상품 속성 창작 없음 |
| C4 | 사용자 피드백→적용 | 선택 지점/전후 버전/행동/앱 판단 근거/실제 호출 연결. 수정 범위 밖 보존 |
| C5 | 완료→재접속 | 문구·이미지·옵션 유지, 실패 후보가 적용되지 않음, 모바일 잘림/가로 넘침/CTA 가독성 |

N과 비율을 모든 사례에 같은 정답으로 강제하지 않는다. 사례의 역할을 충족하고 중복을 줄인 이유가 있으면 허용한다. 생성 요청 크기, 실제 출력 크기, CSS 표시 크기는 서로 다른 값이다. 관찰 불가능한 값은 `unknown`으로 쓰며 모델 설명을 실행 증거로 대신하지 않는다.

## 관찰실과 평가 연결

`/dev/workflows`에서 project ID를 선택한다. `model.request → model.response → model.parsed → workflow.state`, `user.action`, `generation.request/result`, 실제 반환된 `tool.result`의 event ID/run ID/turn ID를 가능한 범위에서 기록한다. 앱이 호출하지 않은 도구나 제공되지 않은 reasoning 요약은 `not_available`이며 실패가 아니다. 대화 요약을 비공개 추론 원문으로 바꾸어 적지 않는다.

품질에 영향을 준 것으로 의심되는 **판단 지점**, 그 전 결과, 그 후 결과를 연결한다. 관찰된 변화와 원인 가설을 분리한다. 동일 모델이라는 사실만으로 인과관계가 입증되지는 않는다.

평가 rubric은 기존 `workflow-quality-v1`: `intent`, `factuality`, `visual`, `image_fit`, `effort`, `satisfaction`. 1 매우 부족 / 2 부족 / 3 수용 가능 / 4 좋음 / 5 매우 좋음, 부담 점수는 높을수록 부담이 적다. 미평가값은 null. 이 실행의 검사 점수는 `developer`; AI 검사자는 note에 `synthetic-e2e; suite=agentic-pages-v1; case=...; run=...`를 붙인다. 케이스의 가상 고객 대사를 `customer_report` 또는 `satisfaction` 점수로 저장하지 않는다. 실제 고객 의견을 별도로 받은 경우에만 출처·원문을 남기고 별도 데이터로 집계한다.

가설·전후 결과·동일 항목/출처/rubric의 점수를 관찰실 실험에 연결할 수 있다. 점수가 올랐다고 자동 도입/배포하지 않는다. 시나리오 실행 식별자·fixture 해시·세부 체크리스트는 현재 별도 DB 컬럼이 없으므로 run 문서가 원장이고 관찰실 note와 연결한다.

## 판정과 비교

- 항목별 `pass / fail / unsupported / blocked_fixture / blocked_input / blocked_environment / blocked_budget / not_run / not_applicable` 중 하나. run 전체는 적용 가능한 모든 필수 항목 pass일 때만 pass. 하나라도 fail이면 fail, 나머지 미완료는 partial/blocked로 표시한다. 조건부 미실행은 not_applicable로 따로 집계하며 그 기능을 검증했다고 주장하지 않는다. 시나리오가 요구한 이미지를 앱이 누락한 경우는 not_applicable이 아니라 fail이다.
- 필수 실패: 상품 정체성 변경, 제공한 가격·구성·사양 왜곡, 미제공 후기/인증/성과 생성, 범위 밖 변경/저장 손실, 실패 후보 강제 적용. 평균 점수로 이러한 실패를 덮지 않는다.
- 이미지 주관 품질에는 스크린샷과 구체적 근거를 붙인다. 창작 문구의 완전 일치나 픽셀 완전 일치를 강제하지 않는다. 다만 보호하는 상품 사실과 수정하지 않은 구조/슬롯은 전후 데이터로 대조한다.
- 질문 수, 필수 승인 수, 최초 가시 초안까지 경과시간, 사용자 대기/활성 처리시간(계측되면), 모델/이미지 호출·재생성 수, 앱 크레딧과 실제 공급자 비용(확인 가능할 때만)을 함께 기록한다. 미수집값을 0으로 넣지 않는다.
- baseline/candidate는 같은 fixture·분기·평가자·모델/설정을 쓰고 바뀐 요소를 하나씩 명시한다. 단일 성공은 재현 표본 1개다. 반복 횟수는 실행 요청에 따르며 표본 수와 실패/미지원 분모를 함께 보고한다. 이 10개를 실제 고객 만족도나 시장 전체 성능으로 일반화하지 않는다.
