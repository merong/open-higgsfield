# 사용자 인터뷰 및 범위 결정

2026-09-28 · 코디네이터 관리 문서

## 확정된 방향

- 목적: 랜딩페이지와 제품 상세페이지의 결과 품질 향상.
- 수단: 사용자 참여형 에이전틱 워크플로우 고도화.
- 분석 대상: 로컬 Open Design의 관련 코드 집중 분석 및 문서화.
- 부수 기능: 전체 구조만 분석. 카드뉴스·릴스 심층 분석 제외.
- 조사 가설: Open Design의 사용자 참여 흐름이 참고할 만할 것으로 예상하지만 실제 구현과 적합성은 확인이 필요하다.
- 별도 Herdr 에이전트가 분석 결과를 근거로 현재 프로젝트와 도입 기능·전략을 리뷰한다.
- 분석 결과와 추가 분석 내용은 사용자와의 딥 인터뷰로 의견을 수렴한다.
- 현 상태: 1차 정적 분석 문서 4종과 결과 인터뷰 6~9를 바탕으로 별도 도입 리뷰 착수. 리뷰 결과에 따라 딥 인터뷰와 필요한 추가 분석을 이어간다.

## 인터뷰 1 — 우선 해결할 품질 문제

질문: 현재 랜딩·상세페이지 결과에서 가장 먼저 해결하고 싶은 품질 문제는 무엇인가? 가장 아쉬웠던 실제 결과 또는 원하는 수준의 예시는?

대화용 선택지:
- 디자인·레이아웃의 획일성 또는 완성도.
- 사용자 의도·상품 특성 반영과 내용·설득 구조.
- 초안 이후 피드백과 수정 과정.

답변: 디자인·레이아웃과 내용·설득 구조 모두 개선해야 한다. 이미지 몇 장이 필요한지, 크기와 내용을 어떻게 구성할지 부족하다. 생성된 이미지의 적절성에 대해 사용자 의견을 수렴하고, 모델·사이즈·내용을 바꿔 재생성할지 후속 조치를 정하는 기능도 보완해야 한다.

확인된 분석 관심사:
- 페이지 구성·디자인 및 내용·설득 구조와 이미지 계획의 연결.
- 이미지 수량·크기·내용을 결정하는 방식.
- 생성 이미지의 적절성에 대한 사용자 피드백 수집.
- 피드백을 모델·사이즈·내용 변경과 재생성으로 연결하는 과정.

미정: 사용자 개입 시점, 크기의 의미(비율·출력 해상도·페이지 표시 크기), 모델 선택을 사용자가 직접 할지 AI가 제안할지, 승인 단위, 재생성 후 비교와 확정 방식. 위 항목을 구현 요구로 임의 확정하지 않는다.

## 인터뷰 2 — 첫 사용자 개입 시점

질문: 페이지 구성과 이미지 계획에 사용자가 처음 참여하는 시점은 언제가 적합한가?

선택지:
- 생성 전 페이지 구성과 섹션별 이미지 역할·수량·내용·비율을 함께 검토하고 확정.
- 대표 섹션과 소수 이미지를 먼저 만든 뒤 방향을 맞추고 전체 제작.
- 전체 페이지 초안을 먼저 보고 이미지별 수정·재생성.

답변: 기존 Openhiggsfield에 'AI와 함께 제작' 기능이 있다. 대표 시안 생성에도 시간이 걸리므로 사용자 선택에 따라 바로 AI 제작을 진행할 수 있어야 한다. 복잡한 입력과 선택을 줄이고, 가급적 적은 입력 데이터로 사용자 의도를 추출하여 작업을 수행하는 것이 핵심이다.

확정된 원칙:
- 기존 'AI와 함께 제작'을 출발점으로 개선한다.
- 계획 검토나 대표 시안 확인을 필수 관문으로 만들지 않는다.
- 사용자가 선택하면 대표 시안을 기다리는 단계 없이 바로 AI 제작으로 진행할 수 있다.
- 사용자 참여 횟수보다 최소 입력에서 의도를 파악하고 품질을 높이는 것이 중요하다.
- 생성 후 이미지 적절성 피드백과 부분 재생성에 대한 앞선 요구는 유지한다.

분석에 반영할 질문: Open Design은 적은 입력에서 요구를 어떻게 추출·유지하며, 어떤 불확실성에서만 추가 질문을 하는가? 기본값·추론·사용자 선택이 실제 실행으로 어떻게 연결되는가? 진행을 막지 않는 피드백과 수정은 어떻게 처리하는가? 해당 기능이 실제 존재하는지는 코드로 확인해야 한다.

## 인터뷰 3 — 의도 추출의 출발 자료

질문: 사용자가 제작을 시작할 때 주로 제공할 최소 입력은 무엇인가? 짧은 설명, 상품 사진, 기존 상품·서비스 URL 등 실제로 가장 흔할 입력 조합을 확인한다.

답변: '짧은 설명 + 상품 사진', '기존 상품·서비스 URL', '간단한 제작 요청 한 문장' 세 가지 모두 적절하다. 사용자는 이 중 한 가지를 선택하고 해당 자료를 입력한다.

확정된 입력 방식:
1. 짧은 설명 + 상품 사진.
2. 기존 상품·서비스 URL.
3. 간단한 제작 요청 한 문장.

세 입력을 모두 필수로 요구하지 않는다. URL 수집이나 사진 해석이 현재 구현돼 있다는 뜻은 아니며, 기존 앱과 Open Design의 지원 여부·처리 경로를 각각 확인해야 한다. 입력 유형별로 의도·사실·이미지 자료를 추출해 페이지 및 이미지 계획으로 연결하는 방식이 분석 대상이다. 정보 부족·URL 접근 실패 등의 처리 정책은 아직 미정이다.

## 인터뷰 4 — 이미지 피드백과 변경 결정

질문: 생성 이미지 수정 시 사용자는 원하는 변화만 말하고 AI가 모델·크기·내용 변경을 판단하는 방식을 기본으로 할 것인가? 필요 시 사용자가 세부 설정을 직접 바꾸는 선택지도 원하는가?

답변: edit 모드에서 이미지 특정 영역에 코멘트를 추가하는 방식과 함께, 사용자가 입력한 텍스트를 기반으로 수정 내용을 제안하는 것도 좋다.

확정된 분석 관심사:
- 이미지 특정 영역을 지정하고 코멘트를 연결하는 edit 모드.
- 사용자의 텍스트를 해석하여 구체적인 수정 내용을 제안하는 흐름.
- 선택 영역·코멘트·텍스트가 수정 대상과 생성 지시로 연결되는 코드 및 데이터 계약.

미정: 영역 코멘트의 UI 형식, 실제 인페인팅 지원 여부·필요성, 수정안 승인 시점, 모델·사이즈 직접 설정 노출, 재생성 후 비교·확정 방식. 이미지 영역 코멘트 기능이 실제 인페인팅을 뜻한다고 단정하지 않는다.

## 인터뷰 5 — 수정 제안과 실행

질문: AI가 코멘트와 텍스트로 수정안을 만들면 사용자 확인 후 실행할 것인가, 아니면 명확한 요청은 바로 실행하고 사실 변경·큰 범위 변경·추가 비용 등 선택이 필요한 경우에만 확인할 것인가?

답변: 판단이 필요한 경우에만 확인하는 방식이 맞으며, 사용자를 가급적 귀찮게 하지 않아야 한다.

확정 원칙: 해석이 명확한 수정 요청은 바로 실행하고, 사용자 판단이 꼭 필요한 경우에만 확인한다. 불필요한 승인·질문·선택을 최소화한다. 어떤 경우에 사용자 판단이 필수인지에 대한 구체적 기준은 코드 분석 사례를 바탕으로 후속 인터뷰에서 정교화한다. 이 원칙이 실제 유료 호출이나 제품 코드 변경을 이번 연구 작업에 허용하는 것은 아니다.

## 1차 분석 착수 기준과 이후 진행

초기 인터뷰에서 목적, 범위, 세 입력 유형, 이미지 기획·피드백, 영역 코멘트, 수정안 제안, 조건부 확인 원칙을 확보했다. 이 기준으로 분석 에이전트가 관련 코드만 1차 집중 분석한다. 미정 항목은 추측으로 확정하지 않는다.

분석 결과를 실제 코드 사례·한계·선택 쟁점과 함께 사용자에게 제시한다. 후속 딥 인터뷰로 추가 분석 필요성과 도입 리뷰 기준을 정한 후 별도 리뷰 에이전트에 전달한다. 리뷰 결과 역시 사용자 인터뷰에서 검토한다.

## 결과 기반 인터뷰 6 — 질문이 필요한 정보 부족의 경계

근거: findings-and-questions.md F1/F2/Q1 및 Open Design apps/daemon/src/prompts/discovery.ts. 분석 복제본의 기본 discovery는 입력이 충분해도 첫 질문 폼을 요구하며, 명시적 바로 제작 등의 예외가 있다. 현재 확정한 최소 질문 원칙에 그대로 맞는 정책은 아니다. 정적 분석 결과이며 실제 모델 동작·품질은 미검증이다.

검토안: 스타일·배치 등은 AI가 정하고, 미제공 가격·규격은 지어내지 않고 해당 정보를 제외하여 진행하며, 판매 대상 자체가 모호해 전체 제작 방향이 달라지는 경우에만 짧게 확인한다.

질문: 위 경계가 적절한가? 가격·규격이 없을 때도 제작 전에 반드시 확인해야 하는 실제 사용 상황이 있는가?

답변: 사용자가 위 기준이 적절하다고 확인했다.

확정 정책: 스타일·색상·레이아웃은 AI가 판단한다. 미제공 가격·규격은 지어내지 않고 해당 정보를 제외하여 초안을 제작한다. 판매 대상이 모호하여 전체 제작 방향이 달라지는 경우에는 대상만 짧게 확인한다. URL 접근 실패 등 다른 정보 부족 상황의 세부 처리까지 확정한 것은 아니다.

## 결과 기반 인터뷰 7 — 이미지 크기 요청의 해석

근거: findings-and-questions.md F3/Q2. 생성 해상도·비율과 페이지의 표시 크기·크롭은 서로 다른 값이다. 특정 템플릿의 이미지 슬롯은 생성 크기로 연결되지만, 사용자 표현을 배치/구도/해상도 변경으로 구분하는 범용 판단 계약은 미확인이다.

질문: '이미지를 더 크게/넓게' 같은 요청은 우선 원본을 유지하는 배치·크롭 조정으로 해결하고, 요청한 구도나 화질을 그 방법으로 충족할 수 없을 때만 재생성하는 것이 적절한가?

검토안: 배치 조정 우선은 기계적인 고정 규칙이 아니라 의도와 품질을 충족하는 가장 작은 변경을 먼저 선택하는 기준이다. 피사체가 잘리거나 화질이 저하되면 단순 확대를 성공으로 처리하지 않는다. 요청이 명확하면 기존 원칙에 따라 실행하고, 해석에 사용자 판단이 필요한 경우에만 질문한다.

답변: 사용자가 위 기준이 적절하다고 확인했다.

확정 정책: AI가 의도와 품질을 충족하는 가장 작은 변경을 선택한다. 배치·확대·크롭으로 해결 가능하면 원본을 유지해 조정한다. 다른 구도·장면이 필요하면 이미지 수정·재생성을 선택한다. 확대 시 흐려짐이나 상품 잘림이 생기면 단순 확대를 완료로 처리하지 않는다. 방법을 매번 사용자에게 고르게 하지 않는다.

## 결과 기반 인터뷰 8 — 영역 수정의 원본 보존

근거: findings-and-questions.md F4/Q3. 영역 코멘트 전달은 확인했으나 실제 마스크 기반 인페인팅 경로와 영역 밖 변경을 막는 보장은 확인하지 못했다. 영역 표시와 실제 부분 픽셀 수정은 구분해야 한다.

사례: 사용자가 상품 사진의 배경을 지정하여 '배경만 밝게'라고 요청했다. 전체 재생성으로 상품의 색상·형태·로고도 달라질 수 있다.

질문: 실제 상품 사진의 상품 정체성(색상·형태·로고 등)은 기본적으로 보존하며, 주변 배경·조명은 요청에 맞게 수정하고, 상품 보존을 충족하기 어려우면 원본 활용 대안을 우선 선택하는 기준이 적절한가? 상품 자체를 변경해야만 요청을 충족할 수 있을 때만 사용자에게 묻는 것을 검토한다.

답변: 사용자가 위 기준을 승인했다.

확정 정책: 실제 상품 사진의 색상·형태·로고는 기본적으로 보존한다. 배경·조명은 요청 범위에서 수정한다. 상품 보존이 어려우면 원본을 활용한 배경 교체·합성을 우선 검토한다. 상품 자체를 바꿔야만 요청을 충족할 수 있을 때 사용자에게 확인한다. 이는 품질 요구이며 현재 도구가 보존을 보장한다는 뜻은 아니다.

## 결과 기반 인터뷰 9 — 수정 결과 적용과 되돌리기

근거: findings-and-questions.md F5/Q4. HTML 버전 복원은 확인했으나 이미지 파일까지 함께 복구하거나 재생성 후보를 비교·채택하는 통합 경로는 미확인이다.

질문: 명확한 수정 결과는 페이지에 바로 적용하고, 사용자가 원할 때 이전 결과와 비교하거나 한 번에 되돌릴 수 있도록 하는 방식이 적절한가?

검토안: 매번 적용 승인을 요구하지 않는다. 이전 이미지 파일을 보존하며 해당 수정에 연결된 문구·배치까지 함께 복원할 수 있도록 한다. 되돌리기가 그 이후의 다른 수정까지 취소하지 않도록 영향 범위를 별도로 설계한다. 결과가 요청을 충족했는지 또는 상품 보존 여부에 판단이 필요한 경우에만 선택을 요청한다.

답변: 사용자가 '네 일단 이 방식으로 진행합니다'라고 확인했다.

채택한 초기안: 명확한 수정 결과는 페이지에 바로 적용한다. 사용자가 원할 때 이전 결과를 비교하거나 한 번에 되돌릴 수 있게 한다. 이전 이미지와 해당 수정에 연결된 배치·문구도 함께 복원한다. 매번 채택 버튼을 요구하지 않고 판단이 필요한 결과만 확인한다. 사용자의 '일단'을 반영하여 리뷰·검증 후 조정 가능한 초기안으로 관리한다.

구현 세부 미정: 이후의 독립 수정과 복원 간 충돌, 저장 단위·보존 기간, 비교 UI, 이미지 변경 검증 방식. 이는 도입 리뷰의 검토 항목이며 사용자 승인 없이 임의 확정한 요구사항이 아니다.

## 별도 도입 리뷰 착수

open-design-review가 분석 문서와 인터뷰 1~9를 기준으로 현재 앱의 실제 코드와 비교한다. 코드 구현은 하지 않는다. 기존에 충족한 기능, 부족한 연결, 채택·변형·보류 후보, 우선 실험과 검증 조건을 정리한다. 추가 분석이 필요한 부분은 이유와 좁은 범위를 제시하고, 사용자 의견이 필요한 쟁점만 후속 인터뷰로 반환한다. 여러 코멘트 처리, URL 접근 실패, 비용·모델 선택의 세부 정책은 아직 미정이므로 확정 사항으로 취급하지 않는다.

## 남은 인터뷰 주제 후보

현재 작업 과정과 실패 사례 → 원하는 품질과 사용자 역할 → 개입 시점·선택 방식 → 참고 서비스에서 기대하는 경험 → 우선 분석 시나리오·합격 기준.

한 번에 핵심 질문 하나를 다루고 답변에 따라 후속 질문을 조정한다. 미응답을 동의나 결정으로 취급하지 않는다. 분석 발견과 리뷰 권고도 후속 인터뷰에 반영한다.
