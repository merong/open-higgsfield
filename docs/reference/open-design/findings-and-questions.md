# 발견과 후속 인터뷰 질문

**1차 분석 종료 후 인터뷰 대기 자료.** 최신 [인터뷰 기록](interview-log.md)의 확정 사항을 다시 의사결정 대상으로 돌리지 않는다. 추가 코드 조사·실행 검증·도입 여부는 이번 문서에서 확정하지 않는다. 실제 앱과의 도입 비교는 별도 리뷰 담당의 범위다.

증거 수준: **사실**은 현재 SHA의 코드/계약/테스트 소스 확인, **추론**은 그 구조에서 예상되는 결과, **미확인**은 실행 또는 연결 증거 부족, **인터뷰 후보**는 아직 합의되지 않은 선택이다. “부분 구현”은 조사 질문에 필요한 연결 일부만 확인했다는 뜻이다.

## F1. 세 입력을 받는 진입점과 상품 의도 추출기는 다르다

**사실:** 텍스트·사진은 동일한 Home/chat 진입점으로 전달된다. URL은 텍스트로 줄 수 있고 브랜드 추출에는 HTML/CSS·로고·문구 수집 구현이 있다. 일반 채팅은 주로 에이전트 도구에 자료 읽기를 맡긴다. [R01](reference-catalog.md#r01) [R07](reference-catalog.md#r07)

**부분 구현/미확인:** 세 입력 유형을 각각 정규화해 판매 대상·확정 사실·추론·출처를 동일한 페이지 계획으로 연결하는 범용 계약은 확인하지 못했다. 브랜드 수집 모듈의 존재가 모든 상품 URL의 본문·사진 수집을 의미하지 않는다. 업로드 실패가 일부 발생하면 성공한 파일만 다음 단계로 전달될 여지도 있다.

**추론:** 최소 입력에서 잘못 추정한 상품을 길게 제작하는 비용을 줄이려면 “진행 가능한 취향의 공백”과 “진행하면 상품 사실이 바뀌는 공백”을 구분하는 것이 중요하다. 구체적 중단 기준은 Q1에서 결정해야 한다.

## F2. 질문을 줄이는 구현은 있지만 일관된 기본 규칙은 아니다

**사실:** 초기 discovery는 풍부한 입력에도 질문을 요구한다. 반면 이미 답한 정보·기존 디자인의 수정·명시적 바로 제작·skipDiscoveryBrief·충분한 memory를 이용한 task-brief 예외가 있다. memory 예외는 확인 대기 없이 계속하라고 지시한다. [R03](reference-catalog.md#r03) [R04](reference-catalog.md#r04)

**부분 구현/미확인:** 이 분기는 대부분 프롬프트다. 질문이 정말 필요한지 측정하는 서버 판단기, 최소 질문 수나 사용자 완료율의 실측은 확인하지 않았다. 특정 랜딩 템플릿은 오히려 8개 입력 질문 그룹을 요구한다.

**분석상 의미:** Open Design이 사용자 참여를 잘 구현했을 것이라는 조사 가설은 일부 UI·맥락 전달에서 근거를 얻지만, 현재 사용자의 “가급적 귀찮게 하지 않기”와 같은 기본 정책이라고 볼 수는 없다. 질문 폼 자체를 도입 성과로 삼을 근거는 부족하다.

## F3. 이미지 계획이 실행값으로 연결되는 사례는 있으나 범용성이 제한된다

**사실:** 일반 페이지 계획은 TodoWrite와 문서/프롬프트 중심이다. 특정 랜딩 템플릿은 슬롯 manifest의 width/height를 실제 생성 요청에 전달하고 파일명으로 HTML에 배치한다. 일반 미디어 dispatcher는 model·prompt·aspect·reference image를 받는다. [R05](reference-catalog.md#r05) [R06](reference-catalog.md#r06) [R12](reference-catalog.md#r12)

**부분 구현/미확인:** 고정 16개 슬롯은 상품·목적에 따른 이미지 수량 최적화가 아니다. 생성 크기/비율과 CSS 표시 크기·크롭이 같은 의미도 아니다. 일반 페이지에서 사용자의 적절성 평가를 재생성 파라미터로 바꾸는 구조화 판단·상태 계약은 확인하지 못했다.

**추론:** 슬롯의 역할과 실제 인자를 연결하는 생각은 참고 가치가 있지만, 해당 템플릿의 수량·스타일·질문 수까지 함께 가져오는 것은 별개의 선택이다. 어떤 “크기”를 사용자가 바꾸는지 Q2가 우선 명확해야 한다.

## F4. 영역 피드백은 실행에 연결되지만 마스크·원문 보호와 같지 않다

**사실:** 요소 코멘트와 Mark에는 선택자, 위치, 스크린샷, 메모를 전달하는 계약이 있다. 메모를 사용자 질의로 승격해 바로 실행/큐에 넣을 수 있다. 범위 밖 변경이면 먼저 질문하라는 프롬프트가 있다. 수동 Edit는 HTML 문구·링크·이미지 src/alt를 직접 바꾼다. [R08](reference-catalog.md#r08) [R09](reference-catalog.md#r09) [R10](reference-catalog.md#r10) [R11](reference-catalog.md#r11)

**부분 구현/미확인:** 주석은 인페인팅 마스크가 아니다. 독립 이미지 파일 뷰어에는 같은 Mark UI가 연결되어 있지 않다. 공통 미디어 API에 mask가 없으며 provider별 참조 이미지 처리에도 차이가 있다. 카탈로그의 inpaint 표시는 이 경로의 완결성 증거가 아니다. AI의 범위 밖 파일 변경과 확정 원문 변경을 이 주석 경로가 프로그램으로 거부한다고 확인하지 못했다.

**추론:** “오른쪽 배경만 바꿔 달라”가 DOM 이미지 배치 수정인지, 전체 이미지 재생성인지, 실제 원본 일부 픽셀 수정인지에 따라 보존 보장이 달라진다. 사용자에게 기술 용어를 먼저 고르게 하기보다 결과 보존 기대를 Q3에서 확인하는 편이 현재 원칙에 맞는다.

## F5. 확인 상태·버전은 있지만 이미지 후보 채택은 별도 문제다

**사실:** 저장 코멘트는 실행 성공 뒤 needs_review가 된다. HTML 버전 미리보기/복원은 있고, 복원도 새 버전이다. 이미지 생성 기본 이름은 고유해지는 구조지만 output을 지정하거나 템플릿 force를 쓰면 기존 파일에 쓴다. [R11](reference-catalog.md#r11) [R12](reference-catalog.md#r12) [R13](reference-catalog.md#r13)

**부분 구현/미확인:** 원본 이미지·페이지 배치·확정 문구를 묶은 불변 스냅샷이나 재생성 후보의 나란히 비교·채택을 이 흐름에서 확인하지 못했다. HTML 복원만으로 덮어쓴 이미지까지 복원된다고 볼 수 없다. 체크리스트/자기평가/선택적 Jury가 실제 최종 화면 품질을 증명하지도 않는다. [R14](reference-catalog.md#r14)

**추론:** 명확한 수정을 바로 실행하면서도 사용자의 확인 부담을 줄이려면 되돌리기의 신뢰성이 중요하다. 다만 모든 수정에 비교·승인을 강제하는지 여부는 이미 확정된 원칙에 어긋날 수 있으므로 Q4에서 필요한 예외만 정해야 한다.

## 후속 인터뷰 — 한 번에 하나씩

다음 순서는 도입 우선순위가 아니라 미정 정책을 좁히는 대화 순서다. 명확한 요청은 바로 실행한다는 원칙, 세 입력 중 하나만 받는 방식, 대표 시안을 필수로 하지 않는 결정은 유지한다.

### Q1. 최소 입력의 어떤 공백만 제작을 멈춰야 하는가?

**실제 사례:** 여러 상품이 들어 있는 사진, 로그인/차단으로 읽히지 않는 상품 URL, 가격·규격 없이 “이 제품 상세페이지”라는 요청. Open Design은 브랜드 자료가 없으면 묻는 지시는 있지만 일반 상품 사실 확인 계약은 없다. [R01](reference-catalog.md#r01) [R03](reference-catalog.md#r03) [R07](reference-catalog.md#r07)

**질문:** 판매 대상이나 핵심 상품 사실을 확정할 수 없을 때만 한 번 질문하고, 스타일·보조 문구·레이아웃은 AI가 정해 진행하는 선이 적절한가? URL 접근 실패 시 읽은 정보만으로 미확인 사실을 비워 둔 초안을 만들지, 자료를 더 받아야 할지도 같은 사례로 확인한다.

- 핵심 사실만 질문: 입력 부담이 작지만 어디까지 핵심인지 경계가 필요하다.
- 가용 자료로 먼저 초안: 빠르지만 미확인 내용·대상 오인이 사용자에게 명확히 보여야 한다.

**아직 정하지 않은 것:** 필수 사실 목록, 사진 대상 선택 UI, URL 실패의 자동 진행 범위. 답변 전 이를 코드 요구로 확정하지 않는다.

### Q2. “이미지를 크게/넓게”의 기본 해석은 무엇인가?

**실제 사례:** manifest width/height는 생성 해상도로 들어가고, 일반 aspect는 provider 픽셀값으로 변환된다. HTML에서 크게 보이는 것은 CSS 배치 문제일 수 있다. [R06](reference-catalog.md#r06) [R12](reference-catalog.md#r12)

**질문:** “대표 이미지를 더 크게”는 우선 페이지의 표시 크기·크롭 조정으로 처리하고, 새 구도나 해상도가 꼭 필요할 때만 재생성을 검토하는 해석이 맞는가?

- 배치 변경 우선: 빠르고 원본 보존에 유리하지만 없는 화면 밖 내용은 만들 수 없다.
- 생성 구도 변경까지 포함: 장면을 바꿀 수 있지만 제품 외형·비용·기존 이미지 유지에 영향이 있다.

**아직 정하지 않은 것:** 비율/해상도/표시 크기의 기본 해석 및 세부 설정 노출. 사용자에게 매번 세 선택을 강제하자는 제안은 아니다.

### Q3. “이 부분만”의 보존 기대와 비용 판단 기준은 어디까지인가?

**실제 사례:** HTML Mark는 빨간 선이 든 스크린샷을 전달한다. 실제 마스크 경로는 확인되지 않았고, 일반 재생성은 다른 부분도 달라질 수 있다. [R09](reference-catalog.md#r09) [R10](reference-catalog.md#r10) [R12](reference-catalog.md#r12)

**질문:** 지정한 부분을 바꾸려면 제품 외형이나 나머지 구도도 달라질 가능성이 있을 때는 확인이 필요한가? 추가로 유료 재생성이 필요한 경우 매번 묻는 대신 사전에 정한 범위 안에서 AI가 진행하는 방식을 원하는지도 이 사례에서 확인한다.

- 결과 보존이 어려운 경우에만 확인: 불필요한 승인을 줄이지만 허용 변화 범위를 알아야 한다.
- 원본 외형이 걸린 이미지 수정은 항상 확인: 보수적이지만 반복 작업의 부담이 커진다.

**아직 정하지 않은 것:** 인페인팅 도입 여부, 승인 없는 지출 범위, 모델 교체 권한. 이번 조사에 유료 호출 권한을 부여하는 질문이 아니다.

### Q4. 재생성 결과는 바로 적용하고 되돌리게 할지, 일부만 비교 후 고를지?

**실제 사례:** 저장 코멘트의 needs_review와 HTML 버전은 있지만 이미지 후보 채택 상태는 미확인이다. 같은 이미지 파일을 덮어쓰면 HTML 복원만으로 픽셀을 되돌릴 수 없다. [R11](reference-catalog.md#r11) [R13](reference-catalog.md#r13)

**질문:** 명확한 수정은 페이지에 바로 적용하되 원본으로 한 번에 되돌릴 수 있게 하고, 제품 외형·대표 이미지처럼 판단이 큰 변경만 전후 비교를 보여주는 흐름이 적절한가?

- 즉시 적용+되돌리기: 클릭 수가 작고 빠르지만 복원 범위가 믿을 만해야 한다.
- 판단이 큰 결과만 비교: 선택을 집중시키지만 어떤 결과가 큰 변경인지 기준이 필요하다.

**아직 정하지 않은 것:** 후보 수, 나란히 비교 UI, 확정 단위, 원본·문구·배치를 함께 보호하는 범위.

### Q5. 짧은 코멘트 여러 개는 한 번에 처리할지, 순서대로 결과를 보여줄지?

**실제 사례:** Open Design의 저장 코멘트 batch는 코멘트 하나마다 별도 queue task를 만든다. 텍스트와 Mark도 큐로 보낼 수 있다. [R11](reference-catalog.md#r11)

**질문:** “제목 줄이기·사진 크게·CTA 바꾸기”처럼 같은 페이지의 명확한 수정은 한 번에 반영하고 결과 요약만 보여주는 편이 좋은가, 아니면 항목별 진행과 결과 확인이 더 중요한가?

- 묶어서 처리: 사용자 왕복이 적지만 변경끼리 충돌하면 해석 정책이 필요하다.
- 항목별 처리: 범위와 진행을 추적하기 쉽지만 반복 실행 시간과 중간 화면 변동이 늘 수 있다.

**아직 정하지 않은 것:** 자동 묶음 기준·상충 피드백 처리·현재 실행 중단/대기 우선순위. 호출 수·속도 개선은 측정되지 않았다.

## 인터뷰 이후에만 검토할 좁은 검증 후보

새로운 광범위 분석이나 구현 계획이 아니라 위 질문의 답을 검증할 예시다.

| 확정할 정책 | 이후 검증 예시 | 관찰할 증거 |
| --- | --- | --- |
| Q1 입력 공백 | 각각 한 문장, 상품 사진+설명, 접근 실패 URL | 필요한 질문 수, 읽은 자료/못 읽은 자료 구분, 없는 사양을 확정하지 않는지 |
| Q2 이미지 크기 | 같은 요청을 CSS 확대·비율 변경·해상도 변경 사례에 적용 | 해석된 변경과 실제 renderer/API 파라미터, 최종 화면의 주요 피사체 보존 |
