## 사용자가 확정한 목적과 범위

Openhiggsfield의 랜딩페이지와 제품 상세페이지 결과 품질을 높이기 위해 사용자 참여형 에이전틱 워크플로우를 고도화한다. Open Design에서 관련 코드만 집중 분석하고 문서화한다. 부수 기능은 전체 구조와 핵심 흐름의 연결 위치만 정리한다. 카드뉴스·릴스는 이번 심층 분석 대상이 아니다.

사용자는 Open Design이 Claude Design을 모방해 사용자 참여 흐름을 잘 구축했을 것으로 예상한다. 이는 조사 동기이자 검증할 가설이다. 기능의 존재·완성도·품질 효과나 Claude Design과의 동등성을 미리 단정하지 않는다.

분석 결과를 기반으로 별도 Herdr 리뷰 에이전트가 현재 프로젝트와 비교하여 도입할 기능·전략을 검토한다. 분석 결과와 추가 조사 방향은 코디네이터가 사용자와 딥 인터뷰하여 결정한다.

## 인터뷰 후 확정할 조사 질문 후보

인터뷰 5에서 명확한 수정 요청은 바로 실행하고, 사용자 판단이 꼭 필요한 경우에만 확인하는 원칙을 확정했다. 불필요한 질문·승인을 최소화하는 설계를 평가한다. 아래 다섯 경로를 1차 분석의 중심으로 삼고, 기능 존재/부재/부분 구현과 근거를 기록한다.

1. 세 입력 유형 중 하나 → 의도·사실·자료 추출 → 페이지 구성.
2. 페이지 구성 → 이미지별 역할·수량·크기·내용 계획 → 실행 지시.
3. 최소 입력으로 바로 제작 → 필요한 경우에만 사용자 확인.
4. 이미지 영역 코멘트 + 사용자 텍스트 → 수정 대상·의도 해석 → 수정안 또는 즉시 실행.
5. 이미지 적절성 피드백 → 모델·크기·내용 변경/재생성 → 결과 비교·확정.

1차 분석은 Open Design 근거 수집과 문서화에 집중한다. 현재 앱에 대한 최종 도입 판단은 별도 리뷰 에이전트가 수행한다. findings-and-questions.md에는 사용자 부담을 줄이는 데 영향이 큰 미해결 쟁점만 추려, 각 쟁점에 실제 구현 사례와 장단점을 제시한다. 1차 결과 후 추가 분석을 스스로 확장하지 말고 사용자 인터뷰를 기다린다.

인터뷰 4에서 이미지 특정 영역에 코멘트를 추가하는 edit 모드와 사용자 입력 텍스트 기반의 수정안 제안이 분석 관심사로 추가됐다. 영역·코멘트·텍스트 → 대상/의도 해석 → 수정 제안 → 실행의 실제 코드·계약을 추적한다. 영역 주석이 실제 인페인팅 구현을 의미한다고 단정하지 않으며, 승인 시점·재생성 후 확정 방식은 추가 인터뷰 대상이다.

인터뷰 3에서 시작 입력은 사용자가 다음 중 하나를 선택하는 것으로 확정했다: (1) 짧은 설명 + 상품 사진, (2) 기존 상품·서비스 URL, (3) 간단한 제작 요청 한 문장. 세 유형 각각에서 의도·사실·시각 자료를 추출하고 페이지·이미지 계획으로 연결하는 경로를 분석한다. 세 가지 모두를 제출하도록 요구하지 않는다. URL 수집·사진 해석의 실제 지원 여부는 확인 대상이며 미리 존재한다고 가정하지 않는다.

인터뷰 2의 핵심 원칙: 기존 'AI와 함께 제작'에서 복잡한 입력·선택을 줄이고 최소 입력으로 의도를 추출해 실행한다. 계획 승인·대표 시안 확인은 필수 관문이 아니며 사용자 선택에 따라 바로 AI 제작이 가능해야 한다. 최소 입력 해석, 추가 질문의 필요성 판단, 추론·기본값의 실행 반영, 흐름을 막지 않는 피드백을 중점 조사한다. 사용자 참여를 늘리는 것 자체를 개선 성과로 보지 않는다.

인터뷰 1에서 사용자는 디자인·레이아웃과 내용·설득 구조 모두를 개선 대상으로 지정했다. 특히 이미지 수량·크기·내용 계획과 생성 후 적절성에 대한 사용자 피드백, 모델·사이즈·내용 변경 및 재생성 후속 조치를 핵심 관심사로 추가했다. 최신 답변과 미정 사항은 interview-log.md를 기준으로 한다.

아래는 구현돼 있다고 가정하는 기능 목록이 아니라, 사용자 답변으로 우선순위를 정할 질문이다.

1. 시작 단계에서 목적·독자·상품 사실·콘텐츠·레퍼런스·스타일 취향을 어떤 대화와 선택으로 구체화하는가?
2. 사용자가 계획·구성·디자인 방향을 어떤 산출물로 확인하고 결정하며, 결정이 프롬프트와 실행에 어떻게 반영되는가?
3. 초안과 미리보기에서 전체/섹션/요소별 피드백이 어떻게 변경 대상·코드·상태로 연결되는가?
4. 승인한 사실·문구·이미지·디자인을 유지하면서 반복 수정하고 버전 비교·되돌리기·중단 재개를 어떻게 처리하는가?
5. 불확실한 요구나 검수 문제를 언제 사용자에게 되묻고, 그 선택이 다음 실행과 최종 페이지 품질에 어떻게 연결되는가?

UI 입력 → 요청/이벤트 계약 → 프롬프트·컨텍스트 → 에이전트/도구 실행 → 저장·미리보기 → 사용자 결정 → 재실행 경로를 추적한다. 주변 어댑터·플러그인·배포·인증·과금은 이 경로를 이해하는 데 필요한 구조 수준에 한정한다.

## 역할과 산출물 소유권

본인은 다음 분석 문서만 소유한다. 모두 이 디렉터리에 한국어로 작성한다.

- README.md: 기준 버전, 전체 구조 요약, 범위, 진행 상태, 인덱스, 한계.
- participation-workflow.md: 확인된 사용자 여정·상태 전이와 코드 실행 경로.
- reference-catalog.md: 집중 분석한 코드·프롬프트·계약·테스트의 참고 목록과 적용 조건.
- findings-and-questions.md: 발견별 근거, 가설과 한계, 후속 인터뷰 질문, 추가 분석 후보.

agent-brief.md, review-brief.md, interview-log.md는 코디네이터 소유다. review/는 별도 리뷰 에이전트 소유다. 공유 환경이므로 다른 작업자의 변경을 되돌리거나 덮어쓰지 않는다. 두 저장소의 제품 코드와 기존 문서는 읽기 전용이다.

## 진행 방식과 완료 기준

인터뷰 → 합의된 범위의 분석 → 근거와 질문 제시 → 사용자 딥 인터뷰 → 필요한 추가 분석 → 별도 도입 리뷰 → 리뷰 결과 인터뷰 순으로 진행한다. 분석 에이전트가 독자적으로 추가 분석 범위를 확대하거나 도입 결정을 확정하지 않는다.

정적 분석, 실행 확인, 추론, 제안을 분리한다. 코드만 보고 출력 품질 개선을 입증했다고 표현하지 않는다. 파일·링크와 주요 근거를 확인한다. 완료 보고는 핵심 발견, 문서 위치, 미확인 사항, 사용자에게 확인할 질문을 포함한다.

checkout/pull/reset/clean, 설치·서비스 실행·유료 모델 호출·커밋·푸시·배포·추가 에이전트 생성은 하지 않는다. 구현은 이번 업무 범위가 아니다.
