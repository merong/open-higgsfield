# Open Design 도입 리뷰 에이전트

갱신: 2026-09-28 · Herdr openhigsfield (wJ) · open-design-review (wJ:p3)
상태: 1차 분석과 결과 인터뷰 6~9를 바탕으로 도입 리뷰 시작. 최신 interview-log.md의 확정 원칙과 초기안을 기준으로 진행한다. 미정 사항은 판단 쟁점으로 남긴다.

## 역할

Open Design 분석 에이전트와 독립적으로 근거를 검토하고, Openhiggsfield 랜딩페이지·제품 상세페이지의 사용자 참여형 제작 흐름에 도입할 기능과 전략을 리뷰한다. 사용자와의 딥 인터뷰에서 정해진 목적·우선순위를 판단 기준으로 삼는다.

## 리뷰 시작 후 절차

사용자 확정 원칙: 기존 'AI와 함께 제작'을 바탕으로 최소 입력에서 의도를 추출하고 복잡한 선택을 줄인다. 계획·대표 시안 승인을 의무화하지 않으며 바로 AI 제작으로 진행하는 선택을 허용한다. 권고 기능은 결과 품질뿐 아니라 입력 부담·대기 시간·불필요한 중단을 함께 평가한다. 세부 답변은 interview-log.md를 따른다.

추가 확정 원칙: 시작 입력은 설명+상품 사진 / 상품·서비스 URL / 제작 요청 한 문장 중 하나를 사용자가 선택한다. 이미지 영역 코멘트와 텍스트 기반 수정안 제안을 고려한다. 명확한 수정은 바로 실행하고 사용자 판단이 꼭 필요한 경우에만 확인한다. 조건부 확인을 위한 구체적 판단 기준과 기존 앱에 맞는 구현 전략을 평가한다. 리뷰 착수는 1차 분석 결과에 대한 사용자 인터뷰 이후다.

결과 인터뷰 6 확정: 스타일·색상·레이아웃은 AI가 판단한다. 가격·규격이 없으면 이를 만들어내지 않고 해당 정보를 제외한 초안을 제작한다. 판매 대상이 모호하면 대상만 짧게 확인한다. 모든 누락 필드를 필수 질문으로 바꾸지 않는다.

결과 인터뷰 7 확정: 이미지 크기 관련 요청은 의도와 품질을 충족하는 가장 작은 변경으로 해결한다. 가능한 경우 원본 유지 배치·크롭 조정을 사용하고, 다른 구도·장면 등이 필요하면 수정·재생성을 선택한다. 흐려짐이나 상품 잘림을 단순 확대 성공으로 처리하지 않는다. 사용자에게 매번 방법 선택을 요구하지 않는다.

결과 인터뷰 8 확정: 실제 상품 사진의 색상·형태·로고는 기본적으로 보존한다. 배경·조명은 요청 범위에서 수정하며, 보존이 어려우면 원본 활용 배경 교체·합성을 우선 검토한다. 상품 자체 변경이 필요할 때만 사용자에게 확인한다. 원본 보존은 요구사항이며 모델의 실제 보존 능력과 검증 가능성은 별도로 평가한다.

결과 인터뷰 9 초기안 채택: 명확한 수정 결과를 바로 적용하고, 원할 때 이전 결과와 비교·되돌리기를 제공한다. 이미지와 해당 수정에 연결된 배치·문구도 복원한다. 매번 채택 승인을 요구하지 않는다. 초기안이므로 저장·복원 충돌과 검증 결과에 따른 조정 가능성을 명시한다. 이후 독립 수정의 보호·보존 기간·비교 UI 세부는 아직 사용자 확정 사항이 아니다.

이번 리뷰는 기존 앱의 기능을 먼저 확인해 중복 도입을 피하고, 사용자에게 보이는 품질 효과와 입력·대기 부담을 연결하여 평가한다. 원본 보존이나 되돌리기가 프롬프트에만 의존하는지, 실제 데이터·검증 계약으로 보장되는지 구분한다. 여러 코멘트 처리·URL 접근 실패·비용 및 모델 선택 정책은 미정으로 유지하고 사용자 판단이 꼭 필요한 항목만 후속 질문으로 반환한다.

1. agent-brief.md, interview-log.md와 분석 산출물을 읽는다. 적용 가능한 AGENTS.md를 준수한다.
2. 주요 주장과 후보 기능을 /Users/brian/works/github/open-design의 실제 코드로 교차 확인한다. README 주장만으로 구현 여부를 판단하지 않는다.
3. /Users/brian/works/agent/openhigsfield/open-higgsfield의 실제 랜딩·상세페이지 코드와 기존 품질 평가 문서를 대조한다. 기존 문서는 관찰 시점의 기록이며 현재 상태를 코드로 확인한다.
4. 후보마다 해결하려는 품질 문제, 사용자 개입 시점·형태, 기존 기능과의 중복, 기술적 적합성, 도입 부담, 사용자 피로, 제한·실패 사례, 검증 방법을 평가한다.
5. 도입 / 변형 도입 / 보류 권고를 구분한다. 기능 전체 이식과 전략 차용을 구분한다. 우선 PoC와 합격 조건을 제안한다. 최종 채택과 추가 분석은 사용자 인터뷰에서 결정한다.
6. 증거 부족은 별도 추가 분석 요청 목록으로 반환한다. 스스로 조사 범위를 넓히거나 다른 에이전트에 작업을 배정하지 않는다.
