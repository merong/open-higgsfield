# Opus 리뷰 반영 작업 목록

2026-09-28 · 코디네이터 정리 · 구현/수정 완료 보고가 아니다

[독립 리뷰](reviews/opus-5.5-high-review.md)의 판정은 **수정 후 진행**이다. backlog·trace 설계·SQL은 리뷰 당시 초안으로 보존한다. 이 문서는 초안의 미정·충돌 부분보다 우선하는 다음 작업 목록이며, 아래 항목이 끝나기 전 초안을 구현 승인된 migration으로 취급하지 않는다.

## 구현 전에 구체화할 항목

| 작업 | 리뷰 근거 | 반영 방향과 완료 증거 |
| --- | --- | --- |
| R01 전달 주체와 순서 | B1 | 요청 commit 직후·trace 조회·서버 시작의 relay 경로를 명시. 프로젝트 registry의 트랜잭션 카운터 또는 순서 의존 없는 projection 중 하나를 선택. 실제 lock 순서는 기존 모든 관련 경로를 대조해 통일. 늦은 commit·ack 전 종료·누락 seq를 재현 |
| R02 생성 예약 registry | M1·M2 | 준비 레코드는 일반 projects에 숨겨 넣지 않고 별도 registry로 관리. 같은 UUID를 최종 프로젝트까지 유지. 직접/템플릿·단발 구성안의 요청 키 수명도 추가. 추천→제작은 creation session 연결. 실제 프로젝트 생성 성공 시 SQLite가 준비된다는 사용자 요구 유지 |
| R03 provider transport | M3·M7·M8 | 원문·request ID·usage·파싱 결과를 분리 수집. 응답 수신 로그는 적용 트랜잭션 실패와 함께 사라지지 않게 저장. 텍스트 복구 불가 unknown과 job 조회 가능 unknown, 늦은 결과 폐기를 구분. 모든 호출을 project/pre-project/non-project로 분류 |
| R04 reasoning 관측 계약 | B2 | 요청 여부를 별도 기록하고 `not_requested/requested_not_returned/returned/unsupported/redacted` 구분. 앱 summary는 assistant 출력, 앱 결정 근거는 decision summary. 실제 provider 요약을 요청하는 모드는 모델 지원 확인 후 분리 도입하며 기준선과 섞지 않음 |
| R05 초기 schema와 open/migration 계약 | M6·Minor | 모든 연결에서 FK 설정/검증, STRICT·상태/JSON 의미 검증, 스키마 버전 단일 원천, migration 실패 rollback, 결정적 projection ID, 순서 할당·local diagnostic 계약을 명문화. 다중 run 사이 참조 일치도 검사. 초안 DDL 재실행을 migration으로 사용하지 않음 |
| R06 기존 프로젝트 적용 | M4 | 신규 생성 시 초기화와 별도로 기존 프로젝트만 최초 기록 전 legacy 초기화 또는 선행 backfill 허용. coverage_start 이전 기록 부재 표시. 게이트를 먼저 켜서 기존 AI 기능을 막지 않음 |
| R07 실제 입력·payload 보관 | M5 | 원본 asset뿐 아니라 변환 파라미터와 실제 전송 바이트 해시를 기록. 일회성 검수 PNG·공개 Blob URL을 포함한 payload 취급 기준 마련. outbox 본문 장기 중복 저장을 피하는 설계 비교. 아래 일관성 조건을 만족하는 안만 채택 |
| R08 개선 순서·측정 | M9 | W04를 W04a 문구/배치와 W04b 이미지 수정 라우팅으로 분리. W04a는 W03 이전 가능, W04b는 W03·W05 이후. W06 변경 단위 보호는 자동 적용 전에 준비. W01은 '기존 정책+계측' 기준선이며 계측 오버헤드 별도 보고 |
| R09 운영 활성화 | B3·M10 | 실제 배포의 영속 디스크·호스트/인스턴스 형태, Node/driver/번들 방식 확인 후 운영 활성화. 로컬 PoC와 운영 배포를 구분. 사용자에게 이미 확인 가능한 환경 사실을 추측으로 답하게 하지 않음 |

## 리뷰 권고를 그대로 적용하지 않을 부분

R07에서 큰 payload를 outbox에서 빼고 SQLite/파일에 직접 쓰는 권고는 저장소 중복을 줄이지만 또 다른 dual-write 공백을 만들 수 있다. 따라서 **durable payload 저장 → 해시/참조가 있는 outbox commit → projection/ack → staging 정리**의 순서, orphan 정리와 파일 누락 복구를 정의한 뒤 선택한다. 단순히 해시만 남기고 원문을 잃는 방향은 채택하지 않는다. 대안은 비밀 제거된 outbox payload의 짧고 명시적인 전달 후 정리 정책이다. 어느 안이든 업무 PG 백업에 남는 범위까지 비교한다.

provider 요약 요청 여부는 '추론 기록' 요구를 무시하는 선택이 아니다. **관찰 전용 계측**과 **provider 요청을 바꾸는 요약 수집 모드**를 구분해 데이터의 출처와 비교 가능성을 확보한다. 요약 없는 모델에서는 사용량·effort·공개 출력·앱 결정 근거를 남기고 비공개 추론을 복원했다고 하지 않는다.

현재 trace 초기화는 신규 프로젝트 생성 성공의 선행 조건으로 유지한다. 초기화에 실패해도 프로젝트 생성 성공을 반환하는 예외는 아직 사용자가 요청하지 않았으므로 임의 도입하지 않는다.

## 다음 인터뷰로 좁힐 정책

- 공개 reasoning 요약 수집을 기본 모드로 할지, 진단 모드로 켤지. 실제 지원 모델을 먼저 확인하고 질문한다.
- 추천만 사용하고 끝낸 세션/실패한 준비 run의 보관, 일회성 비전 입력과 trace 보관·삭제 범위.
- 운영자와 프로젝트 소유자의 상세 trace 열람 범위.
- 실제 기준선 검증의 샘플·반복·비용 상한. 새 유료 호출을 임의 실행하지 않는다.
- 기존 미정인 이미지 재생성 비용, 복원 충돌, URL 부분 실패, 코멘트 묶음 정책은 그대로 유지한다.

기술적으로 확인할 relay·locking·driver·배포 사실·schema 세부는 사용자에게 구현 방식을 고르게 하는 질문으로 넘기지 않는다. 기술 검증 후 실제 사용 판단이 필요한 선택만 인터뷰한다.

## 권고 착수 순서

R01~R07과 R09의 환경 확인 → W00-a 생성/DB 준비 → W00-b 관찰용 턴·도구 기록과 legacy 연결 → W01 기준선 → W06 및 W02 → W04a → W03·W05·W04b → URL·최종 화면 검수·조회 UI.

이 단계에서 완료한 것은 개선 항목, SQLite 설계/DDL 초안, 독립 리뷰, 후속 작업 정리다. 앱의 로그 수집·프로젝트 DB 자동 생성·품질 개선 기능은 아직 구현하지 않았다.
